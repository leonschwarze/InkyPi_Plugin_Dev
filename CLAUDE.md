# InkyPi-Plugins: DWD Wetter, Nextcloud Kalender, Tagesdashboard

Dieses Repository enthält drei Plugins für [InkyPi](https://github.com/fatihak/InkyPi), ein E-Ink-Display auf dem Raspberry Pi. Der Besitzer ist Leon, er spricht Deutsch. Alle Texte auf dem Display, in den Einstellungsseiten und in den Kommentaren sind deutsch.

## Zusammenarbeit

- Antworte auf Deutsch.
- Erkläre bei technischen Aufgaben die Schritte und die Gründe dafür, damit Leon mitlernen kann. Liefere nicht nur fertigen Code.
- Wo es passt, biete am Ende eine kleine Übungsaufgabe an, die das Gelernte festigt.
- Prüfe jede sichtbare Änderung, indem du rendert und dir das PNG ansiehst (siehe „Testen“). Melde erst danach, dass etwas fertig ist.
- Committe oder pushe nur, wenn Leon darum bittet.

Jedes Plugin hat das gleiche Gerüst: `<id>.py` mit der Plugin-Klasse, `plugin-info.json`, `settings.html`, `icon.png` (512×512, schwarze Linien auf transparentem Grund) und `render/<id>.html` + `render/<id>.css`.

### Wichtig: `tagesdashboard/lib/` nie direkt bearbeiten

Das Dashboard bringt Kopien der beiden anderen Plugins mit, damit es sich mit einem Befehl installieren lässt. Änderungen immer in `dwd_wetter/`, `nextcloud_kalender/` bzw. `shared/` machen und danach ausführen:

```bash
python dev/sync_lib.py          # Kopien aktualisieren
python dev/sync_lib.py --check  # vor dem Commit: sind die Kopien aktuell?
```

## Wie InkyPi-Plugins funktionieren

- Die Klasse erbt von `plugins.base_plugin.base_plugin.BasePlugin`.
- `generate_image(settings, device_config)` gibt ein PIL-Bild zurück. Bei Fehlern wird `RuntimeError` mit einer deutschen, verständlichen Meldung geworfen; InkyPi zeigt sie in der Web-Oberfläche an.
- `self.render_image(dimensions, "<id>.html", "<id>.css", params)` rendert ein Jinja-Template (es erweitert `plugin.html`) per Chromium-Screenshot. Vorher `zeichensatz.utf8_templates(self)` aufrufen (alle drei Plugins tun das), sonst rät Chromium den Zeichensatz.
- Die Auflösung kommt aus `device_config.get_resolution()`. Bei `orientation == "vertical"` werden Breite und Höhe getauscht.
- `generate_settings_template()` setzt `style_settings = True`, damit die Stileinstellungen (Hintergrund, Textfarbe) erscheinen. Beim Kalender und beim Dashboard ist `api_key` gesetzt; das App-Passwort kommt über `device_config.load_env_key("NEXTCLOUD_APP_PASSWORD")` aus der `.env` (Web-Oberfläche → API Keys).
- Zeitzone: `device_config.get_config("timezone")`, Standard `Europe/Berlin`.
- Jedes Plugin hat eine Methode `current_time(tz)`. Code fragt die Uhrzeit nur darüber ab, damit Tests sie festsetzen können.
- InkyPi lädt beim Start `plugins/<id>/<id>.py`. Ein Importfehler dort kann den Dienst blockieren; das Dashboard fängt ihn deshalb ab und meldet ihn erst in `generate_image`.
- Installation per `inkypi plugin install <id> <repo-url>`: Das Skript klont das Repo und übernimmt den Ordner `<id>` aus dem Wurzelverzeichnis mitsamt Unterordnern.
- InkyPi speichert die Einstellungen einer Instanz als die Formulardaten beim letzten Speichern (`device.json`) und hat keinen Migrationsmechanismus. Ein Update tauscht nur den Plugin-Ordner; die alten Daten bleiben, bis Leon die Einstellungen neu speichert. Deshalb muss jede Version alte Daten selbst lesen können (siehe unten).

### Konventionen in `settings.html`

- Ein verstecktes Feld `cfgVersion` markiert gespeicherte Einstellungen und ihr Format (0 = ohne Feld, ganz alte Instanzen). Checkboxen haben `value="true"`. Nicht angehakte Checkboxen werden vom Browser nicht gesendet, deshalb gilt: Ist `cfgVersion` vorhanden, bedeutet ein fehlender Schlüssel „aus“, sonst gilt der Standardwert aus `DEFAULTS` im Python-Code.
- **Neue Checkbox:** `cfgVersion` erhöhen, Schlüssel in `SINCE_VERSION` (Python) eintragen und `data-since` an der Checkbox setzen. Ist die gespeicherte Version älter, gilt der Standard statt „fehlt = aus“. Alle drei Plugins haben diesen Mechanismus (Dashboard aktuell 12, Konstante `CFG_VERSION` in `tagesdashboard.py`; Wetter 2, Kalender 1).
- **Schlüssel umbenennen oder Bedeutung ändern:** nie stillschweigend. `cfgVersion` erhöhen und die Regel doppelt einbauen: `migrate_settings()` im Python-Code (am Anfang von `generate_image`, gibt eine Kopie zurück) und `migrate()` in `settings.html` (vor dem Vorbelegen). Beide Stellen müssen dasselbe tun. Werte, die durch die Migration ihre Wirkung verlieren, nicht wegwerfen, sondern auf der Seite zum Übernehmen anbieten (Beispiel: Wetter-Titel). Danach `python dev/test_settings.py` mit einem Fall für die alte Version erweitern.
- Beispiel Wetter, cfgVersion 2 (seit 1.10): Das Titel-Radio `titleSelection` ist entfallen, `customTitle` leer = Ortsname vom DWD. Alte Daten: Titel nur übernehmen, wenn `titleSelection == "custom"` war (Standard war „auto“). Die Ortssuche füllt das Titelfeld nicht mehr aus, ein gefülltes Feld wäre jetzt ein eigener Titel.
- Vorbelegung per JavaScript aus `pluginSettings`, wenn `loadPluginSettings` gesetzt ist. Textfelder und Auswahllisten des Dashboards bekommen ihren Standard aus dem JS-Objekt `DEFAULTS` (Schlüssel = `id` des Feldes).
- Prüfungen vor dem Speichern: `window.handleAction` und `window.openModal` umhüllen (siehe bestehende Dateien).
- Die Ortssuche nutzt Nominatim (OpenStreetMap) direkt im Browser, die Karte Leaflet.
- **Aufbau der Einstellungsseiten (seit 1.10, Variante A, alle drei Plugins):** Klassen `st-*` (gleicher Stilblock in allen drei Dateien, das Dashboard hat zusätzlich `st-pairs`, `st-days`, `st-why`, `st-num`, `st-time`): Abschnitte `st-sec` mit Überschrift `st-h` (Linie darunter), eine Option pro Zeile, Checkboxen als `label.st-check` mit hängendem Einzug. Unteroptionen stehen in `st-sub` (eingerückt, mit `data-parent`) und werden blass (`st-off`), wenn die Hauptoption aus ist; `st-sub` darf verschachtelt sein (Frankreich unter Nachrichten). Messwert-Kacheln im Raster `st-grid`, Terminliste/Woche als Umschalter `st-seg`. Technisches (Einrasten, SSL, Name des Schlüssels) steht unter `<details class="st-more">` „Erweitert“; das klappt von selbst auf, wenn dort etwas vom Standard abweicht. Dashboard: Abschnitte in Tagesreihenfolge (Wetter-Ort, Nextcloud, Wetter mit Regenradar und Luftqualität, Termine, Nachrichten, Zug, Anfahrt, Wäsche, Wochenvorschau, Nachtbild, Festtage), jede Funktion mit Hauptschalter und `st-sub`; lange Regeltexte hinter kleinen Aufklappern `details.st-why`; Zug-Wochentage als Schalter `st-days`; Geburtstagstabelle wird unter 560 px per CSS zur Karte (DOM bleibt Tabelle, weil `fields(tr)` und `tr.nextElementSibling` darauf bauen). Auf schmalen Bildschirmen (≤ 480 px) ist der Einzug der Unteroptionen kleiner. Zeilen mit Zahl/Uhrzeit kurz beschriften („min vor Beginn“), sonst brechen sie auf dem Handy um. `st-sub` hat einen Übergang der Deckkraft (0,2 s) – Screenshots nach dem Umschalten kurz warten.
- **Nie `disabled` für abhängige Felder:** Deaktivierte Felder schickt der Browser beim Speichern nicht mit, der Wert wäre weg (z. B. die Stundenzahl bei abgeschaltetem Graph). Nur optisch abschwächen oder mit `hidden` ausblenden; ausgeblendete und zugeklappte Felder werden mitgespeichert.

## Gestaltungsregeln für E-Ink

- **Schrift:** Jost, überall `font-weight: 600`. Die normale Schnittstärke ist auf E-Ink zu dünn.
- **Kein grauer Text:** keine `opacity` und keine Grautöne für Text. E-Ink stellt Grau als Punktraster dar, dabei zerfallen Buchstaben. Hierarchie nur über die Schriftgröße.
- **Größen:** Alles hängt an der CSS-Variable `--u` (Querformat `min(1vw, 1.667vh)`, Hochformat `min(1.45vw, 0.98vh)`; bei 800×480 ist `--u` = 8 px). Kleinste Schrift etwa `1.7 × --u`.
- **Linien:** mindestens `0.3 × --u`, keine Haarlinien.
- **Farben:** satte Farben nahe der Palette von Farb-E-Ink (Schwarz, Weiß, Rot `#E3001B`, Gelb `#FFC400`, Orange `#FF8C00`, Blau `#0082C9`/`#1E6FD9`, Grün `#2E9E3F`). Icon-Konturen in `currentColor`, damit sie der Textfarbe folgen.
- **Icons:** eigene Inline-SVGs (`dwd_icons.py`, `kleidung.py`), keine fremden Icon-Sets. Wetter-Icons 64er-ViewBox, Messwert- und Kleidungs-Icons 32er-ViewBox.
- **Texte:** Zahlen mit Komma (`de_num()`), Uhrzeiten 24 h ohne führende Null (`7:38`), deutsche Wochentage und Monate aus den Listen im Code (nicht vom System-Locale abhängig). Ausnahme: französische Schlagzeilen bleiben im Original (mit `lang="fr"` und französischer Typografie).
- **Karten rechts über den Terminen** (Zug, Aufbruch, Regenradar, Luft, Wäsche): gleiche Grundform (`.train, .laundry, .trip, .air`, `.nowcast` eigene Regel), Rahmen `0.3 × --u`, Radius `1 × --u`, Icon links (`lw-icon`, 48er-ViewBox), Text in `tr-main` (`tr-top` 2,2 u, `tr-sub` 1,8 u), Stufe als `tr-badge` (grün/gelb/rot). Rot gerahmt = ernst, gestrichelt = unsicher. Die Spalte ist bei 800×480 nur ~360 px breit: Zeilen auf ~36 Zeichen auslegen und mit dreistelligen Werten testen.
- **Testauflösungen:** 800×480 (Inky Impression 7,3″), 480×800 (hochkant), 600×448, 1600×1200.

(Diese Regeln gelten für das Displaybild, nicht für die Einstellungsseiten im Browser.)

## Schärfe auf E-Ink (`eink.py`)

Das Inky Impression 7,3″ (Spectra 6) kann nur sechs Farben: Schwarz, Weiß, Gelb, Rot, Blau, Grün. Der Pimoroni-Treiber rastert alles andere per Floyd-Steinberg. Dabei werden Kantenpixel und Mischfarben zu Pünktchen, Schrift franst aus.

Deshalb rasten alle drei Plugins das fertige Bild selbst auf die Displayfarben ein, bevor InkyPi es an den Treiber gibt:

- Quelle: `shared/eink.py`. Kopien liegen in `dwd_wetter/`, `nextcloud_kalender/` und `tagesdashboard/lib/`; nach Änderungen `python dev/sync_lib.py`.
- Aufruf am Ende von `generate_image`: `eink.prepare(image, device_config, enabled=...)`. Wirkt nur bei `display_type == "inky"`, abschaltbar über die Einstellung `einkSnap`. Bei einem Fehler kommt das Bild unverändert zurück.
- Ablauf in `classify`: Pixel nahe einer Gestaltungsfarbe (`REFERENCES`) gelten als rein. Alle anderen werden als Mischung zweier Farben erklärt (`_unmix`). Kanten werden hart der näheren Farbe zugeschlagen. Flächen werden nur gerastert (Bayer 4×4), wenn es Grau, eine helle Tönung (< 60 % Farbe) oder eine ausgewogene Mischung zweier Farben ist. Kräftige Farben und dunkle Töne werden einfarbig gefüllt.
- Orange gibt es nicht: Es wird zum Schachbrett aus Rot und Gelb. Für Text deshalb kein Orange als Hintergrund. Die markante DWD-Warnung hat einen gelben Grund mit dickem orangem Rahmen.
- Palette: Bei Treiber-Sättigung ≤ 0,5 die reinen Farben, sonst die Mischpalette des Treibers (`palette_for`). Ergebnis: Der Treiber verändert danach 0 Pixel.
- Auf dem Pi in InkyPi: Bildeinstellungen (Sättigung, Kontrast, Schärfe, Helligkeit) auf 1,0 lassen, sonst verfälscht InkyPi die eingerasteten Farben vor dem Treiber. `eink.prepare` protokolliert eine Warnung, wenn das nicht so ist.
- Neue Gestaltungsfarben in `REFERENCES` eintragen, sonst werden sie als Mischfarbe behandelt.

**Schrift:** fontconfig mit Kantenglättung **und** Autohinter (`autohint=true`, `hintfull`, `rgba=none`). Der Autohinter setzt alle Striche einer Schriftgröße auf dieselbe Pixelbreite. `eink.py` macht die grauen Kantenpixel anschließend hart schwarz oder weiß. Graues Rastern gibt es nur in Flächen ab 5×5 Pixeln, nie an Schriftkanten. Auf dem Pi: `/etc/fonts/local.conf` (siehe README). Für Tests: `dev/fonts-eink.conf`, wird von `dev/render.py` standardmäßig gesetzt.

Nicht `antialias=false` verwenden (`dev/fonts-mono.conf`, nur zum Vergleich). Chromium ignoriert in diesem Modus das Hinting bei Webfonts. FreeType rundet dann jeden Buchstaben einzeln, und die Strichstärken werden ungleich; Leon hat das auf dem Display bemerkt. Beschriftungen trotzdem kurz halten (z. B. „Tageslicht“ statt „Sonnenauf-/untergang“).

Testen: `python dev/render.py <plugin> --simulate` speichert zusätzlich `*_display.png` (so sieht es nach dem Treiber aus) und meldet, wie viele Pixel der Treiber noch verändert. Das Ziel ist 0. Optionen: `--display mock` (ohne Einrasten), `--font mono` (ohne Kantenglättung) bzw. `--font aa` (Systemstandard), `--inky-saturation 1.0`. Bei Layout-Änderungen immer die `_display.png` ansehen, nicht nur das Original.

## Datenquellen

**Bright Sky** (`https://api.brightsky.dev`), freie API für Open Data des DWD, ohne Key:
- `/current_weather`: Messwerte der nächsten Station, Felder wie `wind_speed_10`, `wind_gust_speed_10`, `precipitation_60`
- `/weather`: stündliche Werte, Beobachtungen und MOSMIX-Vorhersage, Felder wie `temperature`, `precipitation`, `precipitation_probability`, `wind_gust_speed`, `sunshine` (Minuten), `relative_humidity`, `icon`
- `/alerts`: DWD-Warnungen der Warnzelle; `location.name_short` liefert auch den Ortsnamen
- `/radar` (nur Tagesdashboard, `radar.py`): DWD-Radarkomposit RV, 1 Bildpunkt = 1 km², alle 5 Minuten, mit Vorhersage (Nowcast) für die nächsten zwei Stunden. Werte in 0,01 mm je 5 Minuten (×0,12 = mm/Std.). Parameter: `lat`/`lon` (liegen im mittleren Bildpunkt), `distance` (Meter vom Mittelpunkt bis zum Rand; wir nehmen 2000 → 5×5 Bildpunkte, die volle Karte wären Megabyte), `date`/`last_date` (Standard: 1 h vor der letzten Messung bis 2 h danach – wir fragen ab jetzt − 5…10 min bis + 2 h 10 min), `format` (`compressed` = base64 → zlib → 2-Byte-Ganzzahlen; `plain` = verschachtelte Listen), `tz`. Antwort: `radar[]` mit `timestamp`, `source`, `precipitation_5`; dazu `geometry` und `latlon_position`. Doku: GitHub-Issue jdemaeyer/brightsky#144.

Parameter: `lat`, `lon`, `tz`, bei `/weather` zusätzlich `date` und `last_date`.

**DWD UV-Gefahrenindex** (nur Tagesdashboard): `https://opendata.dwd.de/climate_environment/health/alerts/uvi.json`, Struktur `{"content": [{"city": "Bonn", "forecast": {"today": 1, "tomorrow": 1, "dayafter_to": 0}}, …]}`. Tägliche Höchstwerte für ausgewählte Orte, aktualisiert vormittags. Es gibt keine Koordinaten; der Ort wird über den Namen zugeordnet (Einstellung `uvCity`, sonst der DWD-Ortsname). Ohne Treffer zeigt die Kachel die Bewölkung. Stufen nach WHO/BfS: 0–2 niedrig, 3–5 mittel, 6–7 hoch, 8–10 sehr hoch, ab 11 extrem. Sonnenschutz wird ab UV 3 empfohlen.

**sensor.community** (nur Tagesdashboard, `luft.py`): `https://data.sensor.community/airrohr/v1/filter/area={lat},{lon},{km}` = alle Messungen der letzten 5 Minuten im Umkreis. Ohne Schlüssel, aber **User-Agent ist Pflicht** (die Betreiber wollen den Absender bei zu vielen Anfragen erreichen können). Eintrag: `timestamp` (UTC, `YYYY-MM-DD HH:MM:SS`), `location.indoor` (1 = Innensensor), `sensor.id`, `sensor.sensor_type.name` (SDS011, SPS30, PMS…; BME280/DHT22 liefern nur Temperatur/Feuchte), `sensordatavalues[]` mit `value_type` `P1` = PM10, `P2` = PM2,5 (µg/m³, als Text). SDS011 meldet 999,9 bei Messfehlern. Pro Sensor oft mehrere Messungen im 5-Minuten-Fenster. Die großen Dateien unter `/static/v2/` (alle Sensoren weltweit) sind für den Pi zu groß. Lizenz ODbL. **Aus der Claude-Umgebung nicht erreichbar** – nur gegen `dev/mock_luft.py` getestet.

**Umweltbundesamt, Luftdaten-API** (nur Tagesdashboard, `luft.py`): `https://luftdaten.umweltbundesamt.de/api-proxy/airquality/json?date_from=…&time_from=1&date_to=…&time_to=24&station=DENW062&lang=de` (API v4; Rückfall `…/api/air-data/v3/airquality/json`). Antwort `data = {station: {"beginn": [ende, gesamtindex, unvollständig, [komponente, wert, index, anteil], …]}}`; Stationsschlüssel je nach Version Nummer oder Code, deshalb wird der erste genommen. Komponenten: 1 PM10, 3 O3, 5 NO2, 9 PM2,5 (2 CO, 4 SO2). Zeiten in **MEZ ohne Sommerzeit** (UTC+1), Stunden 1–24, Mitternacht auch als „24:00:00“. Stundenwerte kommen mit etwa einer Stunde Verzögerung. Bonn-Auerberg (Hintergrund, LANUV) = **DENW062**; die Verkehrsstationen Reuterstraße (DENW175) und Bornheimer Straße (DENW176) messen nur NO2/Benzol. Quellenangabe laut UBA: „Umweltbundesamt mit Daten der Messnetze der Länder und des Bundes“. **Aus der Claude-Umgebung nicht erreichbar.**

**Luftqualitätsindex (LQI) des UBA**, Klassengrenzen seit 2025 (Stundenwerte, µg/m³, Obergrenze sehr gut / gut / mäßig / schlecht, darüber sehr schlecht): PM2,5 5/15/30/50, PM10 9/27/54/90, NO2 10/30/60/100, O3 24/72/144/240 (SO2 wie NO2). Der schlechteste Schadstoff bestimmt die Klasse. Mit den strengeren Grenzen kommt „mäßig“ deutlich häufiger vor als früher.

**Bonner Klimasensoren** (Stadt Bonn, seit Oktober 2026, 65 geplant, davon 36 in Betrieb): messen nur Lufttemperatur und relative Feuchte (an einzelnen Standorten Luftdruck), **keinen Feinstaub**. Daten in der Urban Data Platform, sichtbar im Geoportal (`geoportal.udp.bonn.de`, Ebene `klimasensoren_sensoren_nah-klimasensoren_sensoren_fern`). Eine öffentliche API ist nicht dokumentiert (nicht im Open-Data-Portal/OGD-Cockpit); der Geoportal-Server ist aus der Claude-Umgebung nicht erreichbar. Deshalb nicht genutzt.

**Deutsche Bahn, Timetables-API („IRIS“)** (nur Tagesdashboard, `bahn.py`): `plan/{eva}/{yymmdd}/{HH}` = Sollfahrplan einer Stunde, `fchg/{eva}` = alle bekannten Änderungen, `station/{name}` = EVA-Nummer. XML; Zeiten als `yyMMddHHmm` in deutscher Ortszeit. Ein Halt `<s id=…>` hat in Plan und Änderungen dieselbe id. Im Plan: `<tl c="RE" n="10418"/>` und `<dp pt=… pp=… l="5" ppth="A|B|Ziel"/>`; in den Änderungen an `<dp>`: `ct` (neue Zeit), `cp` (neues Gleis), `cs="c"` (Ausfall), `cpth` (geänderter Laufweg). Zwei Adressen: offiziell `apis.deutschebahn.com/db-api-marketplace/apis/timetables/v1` mit Headern `DB-Client-Id`/`DB-Api-Key` (kostenlos, .env `DB_CLIENT_ID`/`DB_API_KEY`), sonst ohne Schlüssel `iris.noncd.db.de/iris-tts/timetable` (inoffiziell). Lizenz CC BY 4.0 (Deutsche Bahn AG). Bonn Hbf = EVA 8000044. Düsseldorf Hbf = 8000085.

**Störungsmonitor (`bahn.alerts`):** Meldungen `<m>` hängen am Halt, an `ar` oder `dp`: `t` = d (Verspätungsgrund, nur Code `c`), f/q (Qualität), h (HIM-Freitext in `ext`, Kategorie `cat`, gültig `from`–`to`), r (Störung); `pr` 1 hoch … 4 erledigt; `del="1"` gelöscht; `int` ist intern und wird nie gezeigt. Code-Texte in `bahn.CODES` nach Travel::Status::DE::IRIS (inoffiziell, aber gepflegt). Gezeigt werden nur Meldungen an genau dieser Fahrt, an Abfahrt und Ausstieg (`trainTarget`). Den Ausstieg findet `target_stop` über die Fahrt-ID: Halt-IDs sind `<Fahrt>-<Startzeit>-<Haltnummer>`, die ersten zwei Teile sind an allen Halten gleich (`trip_key`); Zugnummer als Rückfall. Gesucht wird in den Plänen der Abfahrtsstunde und zwei weiteren, das Ergebnis gilt den Tag (`_target_cache`). Regeln: vom Verspätungsgrund nur der neueste und nur bei echter Verspätung/Ausfall (sonst steht ein alter Grund da), Qualität nur `QUALITY_SHOWN`, „Information“ ohne Text weg, abgelaufene weg; rot = r, pr 1, `SEVERE_CODES`. Ausstieg ausgefallen (cs=c oder nicht mehr im `cpth`) → Zustand `partial`, Badge „Teilausfall“. RIS::Disruptions (die eigentliche Störungs-API) ist kostenpflichtig und nur für DB-Vertriebspartner, Schema nicht öffentlich – deshalb nicht genutzt. Jede Meldung bekommt `kind` (`reason`, `quality`, `notice` = Freitext h/r).

**VRR-Fahrplanauskunft, Streckenmeldungen** (nur Tagesdashboard, `strecke.py`, seit 1.13, Einstellung `trainRoute` unter `trainAlerts`): `https://openservice-test.vrr.de/static03/XML_ADDINFO_REQUEST?outputFormat=rapidJSON&filterPublicationStatus=current` – VRR „Open Service“ (opendata-oepnv.de), ohne Anmeldung für private/Test-Nutzung (Nutzungsvereinbarung API), Testkopie der Produktivumgebung (gelegentlich unplausibel; Produktivserver nur auf Anfrage per Mail). Antwort `{"infos": {"current": [...]}}`, ganz NRW, ~1100 Meldungen, ~4 MB. Je Meldung: `id`, `type` (`tripMessage` bei Zügen), `priority` (fast immer „normal“ – taugt nicht als Filter), `timestamps.creation` und `validity[{from, to}]` (UTC mit `Z`; `to` kann fehlen), `infoLinks[0]` (`title`, `subtitle`, `content` als HTML), `properties.providerCode`, `affected.lines[]` (`id` z. B. `ddb:90RE5: :H:`, `number` „RE5“, `operator`, `destination`). Zugmeldungen haben **keine** `affected.stops` – Orte nur im Text. Quellen (providerCode) bei Zügen: **ZTP-PROD** = Streckenstörungen und Baustellen im NRW-Nahverkehr, zeitnah und mit festem Satzbau („Strecke zw. A und B beeinträchtigt - Grund“, „Region X beeinträchtigt“, „… gesperrt“/„nicht befahrbar“, „Reparatur … beendet“, „Maßnahmen und Fahrpläne: RE 5 (RRX)“, „Teilausfälle zwischen …“, „Vorankündigung …“); **DBProd** = HIM der Bahn (Bistro, Fahrräder … – kennt IRIS schon, wird übersprungen); dazu NWL u. a. (meist Busse). Filter: Linie über `number` (Achtung: „RE5“ gibt es auch in Hessen `ddb:90RE5:H:H:` und Hamburg `ddb:90H05`), dann Ort: `route_of` baut den Laufweg aus IRIS (`ar ppth` vor dem Einstieg + Einstieg + `dp ppth`), `on_route` sucht erst Bahnhofsnamen (längste zuerst, „Hauptbahnhof“ = „Hbf“), dann im Rest die Städte des Abschnitts bis zum Ausstieg (erstes Wort vor Leerzeichen/Bindestrich: „Köln-Mülheim“ → Köln). Treffer vor dem Ausstieg → ja; nur der Ausstieg → ja; Bahnhöfe hinter dem Ausstieg → nein, und dann zählt auch die Stadt des Ausstiegs nicht („Düsseldorf-Derendorf–Düsseldorf Flughafen“). Hat der Titel einen Ort, entscheidet er (sonst nennt der Text der Großbaustelle Oberhausen–Emmerich irgendwann Duisburg). Gültig, wenn ein `validity`-Abschnitt [jetzt, Ankunft] berührt; „beendet“ nur 60 min nach `creation`; Vorankündigungen und „Bitte beachten …“ weg. Texte (`describe`): „Strecke Köln-Mülheim–Leverkusen Mitte: Reparatur an einem Signal · seit 6:40“ (Beginn = `validity.from`, sonst `creation`), „Strecke … gesperrt: …“, „Behoben: Signal Köln–Köln Messe/Deutz · Verspätungen möglich“, „Baustelle Düsseldorf–Köln-Mülheim: Umleitungen und Teilausfälle bis 4.12.“ (aus „zu … zwischen A und B.“; „Teilausfällen“ → „Teilausfälle“; „bis“ nur, wenn das Ende < 60 Tage entfernt ist). Geschützte Leerzeichen (`NB`) um „· seit 6:40“ und „bis 4.12.“, damit hochkant nicht „seit“ allein am Zeilenende steht. Alle Streckenmeldungen sind `level` „info“ (gelb), `source` „route“, `kind` acute/done/build. Reihenfolge (`bahn.merge`): rot am Zug → Freitext der Bahn am Zug (kennt die Störung dann schon, genauer) → Strecke akut → Strecke behoben → übrige Hinweise am Zug → Baustellen. Template: Streckenmeldungen mit Gleis-Symbol (perspektivisches Gleis, 16er-ViewBox) statt „!“. Abruf nur im Zug-Zeitfenster, 10 min im Modul (auch Fehlschläge, damit nicht jede Runde 20 s Timeout), User-Agent wie bei der Luft. Ohne Ausstieg oder Ausstieg nicht im Laufweg → keine Streckenmeldungen. **Aus der Claude-Umgebung nicht erreichbar** – getestet gegen `dev/mock_vrr.py` und einen Auszug von Leons echtem Abruf (`dev/vrr_addinfo_2026-11-13.json`, 10:31 Uhr: einzig relevant war die Baustelle Düsseldorf–Köln-Mülheim bis 4.12.).

**Nachrichten (RSS)** (nur Tagesdashboard, `nachrichten.py`): Bonn = General-Anzeiger `https://ga.de/feed.rss`, gefiltert auf Links mit `/bonn/`; NRW = WDR `https://www1.wdr.de/uebersicht-100.feed`; Bund = tagesschau `https://www.tagesschau.de/index~rss2.xml`; optional France = franceinfo „Les titres“ `https://www.francetvinfo.fr/titres.rss` (seit 1.11, `newsFrEnabled`, Standard aus; Alternative Le Monde `https://www.lemonde.fr/rss/une.xml`). Dubletten werden über Wortüberschneidung (Jaccard ≥ 0,4) erkannt; Auswahlreihenfolge Bonn → Bund → NRW, damit Bundesthemen bei der tagesschau bleiben. Bonn wird bei Bedarf mit WDR-Meldungen ergänzt, die „Bonn“ enthalten; NRW nimmt Bonner WDR-Meldungen nur, wenn nichts Landesweites mehr da ist. B. „SNCF.“). `fr_typo()` setzt geschützte Leerzeichen vor `: ; ? !` und in `« »`. Feeds werden 15 Minuten im Speicher gehalten. Die Feed-Adressen wurden über Verzeichnisse geprüft, nicht live aus dieser Umgebung (kein Netz zu den Verlagen).

**Transitous** (nur Tagesdashboard, `anfahrt.py`): `https://api.transitous.org`, MOTIS-2-API, ehrenamtlich betrieben, frei für FOSS und nicht-kommerzielle Nutzung (Usage Policy auf transitous.org/api), kein Schlüssel. `/api/v1/geocode?text=…&place=lat,lon&numResults=1` → `[{lat, lon, name, …}]`. `/api/v6/plan` (Rückfall `/api/v5/plan` bei 404) mit `fromPlace`/`toPlace` = `lat,lon`, `time` (UTC, ISO), `arriveBy=true`. Rad: `directModes=BIKE`, `transitModes=` leer (bei HTTP 400 ohne), `maxDirectTime=5400` → Ergebnis in `direct[]`. Daten in Deutschland: DELFI-Fahrplan (bundesweit, auch VRS/SWB) und DELFI-Echtzeit (GTFS-RT, Abdeckung je Verbund unterschiedlich; ob Bonner Busse Echtzeit haben, zeigt die Transitous-Karte). ## Bekannte Stolperfallen

- **Zeichensatz (seit 1.11 behoben):** InkyPis `base_plugin/render/plugin.html` hat kein `<meta charset>`. InkyPi schreibt die Seite als UTF-8 in eine Datei, Chromium rät den Zeichensatz aber aus dem Inhalt – bei vielen Akzenten (französische Schlagzeilen) als Latin-1, dann steht auf der ganzen Seite „Ã©“ statt „é“ und „Ã¼“ statt „ü“. Ein `<meta>` im eigenen Template hilft nicht (es muss in den ersten 1024 Bytes stehen, davor kommen die `@font-face`-Regeln). Lösung: `shared/zeichensatz.py` legt sich vor den Jinja-Lader des Plugins und ergänzt in `plugin.html` direkt nach `<head>` die Zeile `<meta charset="utf-8">`; sonst bleibt InkyPis Basis-Template unverändert (Updates wirken weiter). Aufruf vor `render_image` in allen drei Plugins; Bilder ohne Akzentproblem bleiben pixelgleich.
- **Jinja:** Dictionary-Schlüssel, die wie Methoden von `dict` heißen (`items`, `values`, `keys`, `get`, `update`), kollidieren: `{{ d.values }}` liefert die Methode („<built-in method values …>“), `{% for x in d.items %}` schlägt fehl. Andere Namen verwenden (`events`, `pieces`, `reading`). Bei der Luftkarte (1.12) ist das mit `values` passiert.
- **Mocks:** Die Mocks ersetzen `requests.Session.get`. Module müssen deshalb über eine `Session` abrufen (`session.get(...)`), nicht über `requests.get` – das läuft über `Session.request` am Mock vorbei ins Netz. Jeder Mock merkt sich den vorherigen `get` und reicht fremde Adressen weiter.
- **Jinja-Autoescape:** SVG-Strings brauchen `| safe`.
- **CSS:** Klassennamen des Wurzelelements (z. B. `.agenda`, `.week`) nicht für innere Elemente wiederverwenden. Das hat schon einmal das ganze Grid-Layout zerschossen.
- **Headless-Chrome:** Die Seite wird zuerst mit kleinerem Fenster aufgebaut und für den Screenshot vergrößert. Skripte, die messen (z. B. Termine kürzen und „+ 3 weitere Termine“ anzeigen), müssen per `ResizeObserver` neu messen.
- **Tests:** Nicht `datetime` im Modul durch eine Unterklasse ersetzen, das bricht `isinstance(x, datetime)` in `to_local()`. Stattdessen `current_time()` überschreiben.
- **Einstellungsseiten:** `disabled` an Formularfeldern löscht beim Speichern deren Wert (siehe Konventionen). InkyPis Entwicklungsserver lädt Templates nur beim Start; nach Änderungen neu starten. Bei Einstellungen ohne `cfgVersion` (Version 0) gilt ein gespeichertes `"false"` – beide Seiten lesen es (bei Kalender und Dashboard fehlte das bis 1.9.1, `test_settings.py` hat es gefunden).
- **Gefühlte Temperatur** (`feels_like`): Windchill erst ab ≤ 10 °C, Hitzeindex ab 26,7 °C; dazwischen gilt die Lufttemperatur.
- **Bright Sky:** `precipitation` gilt für die vorangegangene Stunde. Tageskurve und Texte („Regen 17–23 Uhr“) verwenden einheitlich den Zeitstempel des Datensatzes.
- **Regen in der Tageskurve (Dashboard):** Regen hat eine eigene Zeile unter der Temperaturkurve. Balkenhöhe = Menge in mm/Std. (feste Skala `RAIN_SCALE` = 4 mm, damit Tage vergleichbar bleiben), Füllung = Stärke nach `RAIN_LEVELS`: leicht < 1 (blau umrandet), mäßig < 4 (blau), stark ≥ 4 mm/Std. (rot, wie beim Regenradar). Die Legende zeigt nur die Stufen, die vorkommen. Keine Mengenbeschriftung in der Kurve (wurde abgeschnitten); Zeitraum und Summe stehen in der Kopfzeile. Keine hellen Flächenfarben: Hellblau wird auf E-Ink fast weiß. Das Einzel-Plugin `dwd_wetter` zeigt noch Wahrscheinlichkeitsbalken in Hellblau.
- **Regenradar (`radar.py`, seit 1.11, Variante B):** Karte rechts über den Terminen (Klasse `.nowcast`, wie Wäsche/Anfahrt), nur in der normalen Ansicht und nur, wenn es in den nächsten zwei Stunden am Ort nass wird; sonst bleibt das Bild pixelgleich. Wert am Ort = **stärkster** Wert im Umkreis von 1 km (3×3 Bildpunkte, `POINT_R`): Radar und Nowcast sind etwa 1 km unscharf, und lieber einmal zu vorsichtig. Dadurch ist auch egal, ob Zeile 0 Norden oder Süden ist. Nass ab `WET_MMH` 0,2 mm/Std. (darunter Radarrauschen); Pausen unter `DRY_GAP_MIN` 15 min gehören zum selben Regen (`episodes`). Texte: kommt „Regen 16:35–17:05“ bzw. „Regen ab 16:35“ (hält über den Horizont an); regnet gerade „Regen bis etwa 16:55“ bzw. „Regen hält an“; Zeile 2 Stärke (leicht/mäßig/stark wie die Tageskurve) und „ab 17:45 wieder“, „wieder 17:45–18:10“ oder „danach trocken bis 18:20“ (bis zum Ende der Vorhersage – mehr wissen wir nicht). Uhrzeiten, keine Countdowns (15-Minuten-Takt). Das Radar kennt die Art nicht: `precip_word()` nimmt „Schnee“/„Niederschlag“ aus der Stundenvorhersage (−1 h bis +3 h). Rahmen blau, bei starkem Regen rot. Balkenband: ein Balken je 5 Minuten, Höhe wie die Tageskurve (4 mm/Std. = voll, mindestens 28 %); Ticks nur an vollen Stunden zwischen 22 % und 88 % der Breite (sonst kollidieren sie mit „jetzt“ oder dem Rand). Im Nachrichtenfenster ist das Band ausgeblendet (`.has-news .rd-stripbox`), damit noch Schlagzeilen passen. Mit Zugkarte samt Störungsmeldungen und Radar zugleich bleibt quer trotzdem kein Platz für Schlagzeilen (seltener Fall, bewusst so). Abruf 4 min im Modul gehalten; Fehler → nur Logzeile, kein Bild verloren. Mock-Szenarien in `dev/mock_radar.py` liefern den angefragten Ausschnitt (Zellen ziehen mit 30 km/h aus Südwest). Live noch ungeprüft: Liefert `/radar` mit `date` ≈ jetzt wirklich die zwei Stunden Vorhersage? Stimmen die Einheiten? Passt die Größe zu `distance`?
- **Luftqualität (`luft.py`, seit 1.12, Variante B):** Karte `.air` zwischen Radar und Wäsche, nur in der normalen Ansicht und nur ab der eingestellten Klasse (`airLevel` 3 = mäßig, 4 = schlecht); sonst bleibt das Bild pixelgleich. Feinstaub von sensor.community: nur Außensensoren, frische Messungen (≤ 20 min), Fehlwerte (≥ 999, < 0) weg, je Sensor gemittelt, Median über mindestens `MIN_SENSORS` (3) Sensoren, dann über die Abrufe der letzten Stunde gemittelt (`_history`, Modulspeicher; nach Neustart beginnt das Mittel neu). Quellenwahl in `assess`: Feuchte ≥ `HUMID_RH` (80 %, DWD-Stundenwert am nächsten zu jetzt) oder zu wenige Sensoren → Messstation; beides fehlt → Sensorwert, Karte gestrichelt (`aq-unsure`) mit „Feucht: Sensoren zeigen oft zu viel“. Ozon/NO2 nur mit `airGases`, immer von der Station. Die Station wird nur abgefragt, wenn sie etwas ändern kann (Gase an, Sensoren fehlen oder feucht). Zwischenspeicher: Sensoren 10 min, Station 30 min (auch Fehlschläge). Anzeige: Kopfzeile „Feinstaub erhöht/hoch/sehr hoch“ bzw. „Ozon hoch“ mit Stufe als Plakette rechts (`aq-head`, damit die Messwertzeile die volle Breite hat), Messwertzeile „PM2,5 22 · PM10 39 · 9 Sensoren“ bzw. „· Station“ (Einheit weggelassen, sonst passt sie bei dreistelligen Werten nicht), Hinweis nach UBA (gekürzt). Gelb = mäßig, Rot = schlecht, dicker roter Rahmen = sehr schlecht. Im Nachrichtenfenster ohne Hinweiszeile (`.has-news .aq-advice`). Setzt keine Fenstergrenzen für den Bild-Cache.
- **Termin-Rohdaten:** `events_on_day()` im Kalender gibt in jedem Eintrag unter `source` den Rohtermin (Start/Ende) mit; das Dashboard braucht ihn für das Regenrisiko am Termin.
- **DWD-Layout:** Standard sind 6 Kacheln (Luftdruck, Sichtweite, Taupunkt aus). Ab 7 Kacheln schaltet das Template auf `.dense`, im Querformat mit Warnzeile zusätzlich `.tight`; beide zusammen blenden die Symbolzeile im Graph aus, damit der Graph lesbar hoch bleibt. Die Temperaturfläche unter der Kurve ist ausgeblendet (Farbverlauf wird auf E-Ink grob gerastert).
- **Zug und Aktualisierung (Dashboard):** Die Zugkarte erscheint nur an den gewählten Wochentagen im Zeitfenster. Damit sie aktuell ist, laufen InkyPi-Wechselintervall und Plugin-Intervall auf 5 Minuten. Außerhalb des Fensters gibt `generate_image` bis zu `quietMinutes` (Standard 15, mit 1 Minute Toleranz) dasselbe Bild aus dem Modul-Cache `_IMAGE_CACHE` zurück, höchstens bis zur nächsten Fenstergrenze. **Der Cache ist nur aktiv, wenn der Zug eingeschaltet ist.** Sonst gilt allein das Intervall der Playlist. (Fehler in 1.3: Der Cache lief auch nur mit Nachrichten und verdoppelte so Leons 15-Minuten-Takt auf 30 Minuten. Test: `/tmp`-Skript mit 15-Minuten-Takt, jede Aktualisierung muss „neu“ sein.) InkyPi erkennt das gleiche Bild am Hash und lässt das Display in Ruhe. „Jetzt aktualisieren“ in der Web-Oberfläche umgeht den Cache: `_manual_refresh()` sucht im Aufrufstapel nach InkyPis Klasse `ManualRefresh`. Wird diese Klasse in InkyPi umbenannt, greift der Cache auch bei manueller Aktualisierung (höchstens `quietMinutes` lang). Die Radar-Karte setzt keine eigenen Fenstergrenzen; sie kann also bis zu `quietMinutes` alt sein (Uhrzeiten bleiben trotzdem richtig).
- **Zwei Intervalle in InkyPi („das Display ändert sich nicht“, `src/refresh_task.py`, `src/model.py`):** (1) **Playlist-Takt** `plugin_cycle_interval_seconds` (Einstellungen → Plugin Cycle Interval; Leons Sollwert 15 Minuten): Der Hintergrund-Thread schläft so lange und prüft dann `PlaylistManager.should_refresh`. Ist der Takt zu lang, sieht InkyPi gar nicht nach (Log `Not time to update display`). Am 11.11.2026 stand er versehentlich auf 5 Stunden: Die Wäsche-Karte blieb nach 21:45 stehen. (2) **Intervall der Plugin-Instanz** (`refresh.interval` bzw. `refresh.scheduled`, Uhr-Symbol am Eintrag in der Playlist): Ist es länger als der Takt, lädt InkyPi bei den Zyklen dazwischen nur das gespeicherte PNG (Log `Not time to refresh plugin instance, using latest image`). `generate_image` läuft dann nicht, und keine Fenstergrenze des Dashboards kann greifen. Es soll höchstens so lang sein wie der Takt. Mehrere Instanzen in der Playlist kommen reihum dran: pro Zyklus eine, jede also nur alle N Takte. (3) **Bildvergleich:** Aus dem Ergebnis wird ein SHA-256 über die RGB-Pixel gebildet; ist er gleich dem des angezeigten Bildes, loggt InkyPi `Image already displayed, skipping refresh` und lässt das Display in Ruhe (`refresh_time` wird trotzdem fortgeschrieben). Ein einziges geändertes Pixel löst ein vollständiges Neuzeichnen aus. Fehlersuche auf dem Pi: `journalctl -u inkypi.service --since "21:00" | grep -E "interval refresh check|Not time|Refreshing plugin|using latest image|skipping|Updating display|Luft:"`; in der Web-Oberfläche zeigt der Playlist-Eintrag „Refreshed vor …“ (Zeit der letzten echten Neuberechnung). Alle Fenster und Caches des Dashboards (`quietMinutes`, Wäsche 17–23, Nachtbild, Nachrichten) setzen einen Takt von höchstens etwa 15 Minuten voraus; bei längerem Takt verschiebt sich jede Grenze um bis zu ein Intervall. Simulieren lässt sich das mit InkyPis echten Klassen (`PluginInstance.should_refresh`, `PlaylistManager.should_refresh`, `compute_image_hash`) und eingefrorener Uhr in einem Einmal-Skript (liegt nicht im Repo).

## Entscheidungen

- Farben werden in den Plugins eingerastet statt vom Treiber gerastert (siehe „Schärfe auf E-Ink“).
- Abends: Wäsche-Karte statt Müll-Erinnerung (Leon stellt keine Tonnen raus).
- Nachtbild und Wochenvorschau am Sonntagabend: von Leon gewünscht (Nachtbild hell, nicht schwarz – morgens gut lesbar).
- Nachrichten: Variante D (heute + Schlagzeilen) gewählt; A (statt Tageskurve), B (über den Terminen), C (Band) verworfen. Quer ist Zielformat, hochkant wird immer mitgeprüft.
- Anfahrt: Variante C (Zeile an jedem Termin + Aufbruch-Karte) gewählt; A (nur Zeile) und B (nur Karte) verworfen. Rad nur bei schönem, sicher trockenem Wetter; Heimweg-Wetter als Option, standardmäßig aus. Bei Regen ÖPNV, nicht zu Fuß. Datenquelle Transitous (eine Quelle für Orte, Rad und ÖPNV mit Echtzeit), Rückfall Schätzung.
- Festtage: Variante B (Gruß im Kopf) + C (Festansicht im Zeitfenster). Motive Weihnachten (Bonn im Schnee) und Silvester/Neujahr (Feuerwerk, Fallblatt) freigegeben; Geburtstag: erstes Motiv (Wimpel, Ballons, Torte) abgelehnt, aus A (Ganz Bonn gratuliert), B (Extrablatt), C (Folienballons) wählte Leon C. Geburtstage als eigene Liste, nicht aus dem Kalender (dort stehen auch Leute außerhalb des Haushalts).
- Im Dashboard ersetzt der UV-Index den Luftdruck, weil der Druckwert für Laien wenig aussagt. Im Einzel-Plugin `dwd_wetter` ist der Luftdruck weiterhin wählbar.
- Einstellungsseiten Wetter/Kalender/Dashboard (1.10): Variante A (gegliedert, alles sichtbar, Technik unter „Erweitert“) gewählt; beim Dashboard nur lange Erklärtexte hinter kleinen Aufklappern; B (Kachelauswahl zusätzlich aufklappbar) und C (Live-Vorschau des Titels/der Kachelwirkung) verworfen. Wetter-Titel: ein Feld statt Radio + Feld, mit Migration (cfgVersion 2).
- Regenradar (1.11): Variante B (eigene Karte rechts mit Text und Balkenband, nur wenn Regen kommt) gewählt; A (fein in der Tageskurve) und C (kleine Radarkarte mit Rhein, Ringen, Zugrichtung) verworfen. Datenquelle Bright Sky `/radar` (DWD RV).
- Frankreich (1.11, aus der Ideen-Runde vom 13.11., „gerne in Originalsprache“): Variante A (vierte Ebene „France“ mit Trikolore) gewählt; B (Block „À la une“ unter den Schlagzeilen) verworfen. Quelle franceinfo, Standard aus.
- Luftqualität (1.12): Variante B gewählt (Karte nur, wenn die Luft mäßig oder schlechter ist); A (feste Kachel, zeigt fast immer „gut“) und C (eigenes Plugin mit Karte und 24-h-Verlauf) verworfen. Quelle sensor.community mit der UBA-Station Bonn-Auerberg als Rückfall (auf Leons Wunsch); Ozon/NO2 der Station nur auf Wunsch (Standard aus, sonst käme die Karte im Winter abends oft wegen NO2). Bonner Klimasensoren der Stadt geprüft: messen keinen Feinstaub, keine API.
- Streckenmeldungen (1.13): Variante A gewählt (zusätzliche Zeile im Störungsmonitor mit eigenem Symbol); B (eigenes Feld „Strecke ok/gestört“ in der Zugkarte) und C (Vorwarnung schon vor dem Zeitfenster) verworfen. Quelle VRR-Auskunft statt RIS::Disruptions (kostenpflichtig). Vorwarnung immer gelb. Baustellen auf dem Abschnitt werden mitgezeigt (stehen hinter allem anderen). Idee aus dem Gespräch, nicht gebaut: Verspätung der Züge vor dem eigenen auf demselben Abschnitt (aus IRIS) als zweites Signal.
